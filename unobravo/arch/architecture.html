Architecture map

A canvas engine, wrapped in one very large React class.

What you need in your head before editing anything here: what the parts are, how state actually flows, and which files will bite you quietly rather than loudly.

02 · Package map

Seven workspaces, three real cycles

The intended layering is common → math → element → excalidraw. Arrows point from importer to imported. Reality bends in four places, and each one limits what you can refactor.

What this means in practice

element cannot be lifted out of the React package. 33 files in element and 5 in common import types from @excalidraw/excalidraw/types — all type-only, so there is no runtime edge, but AppState lives in the React package and the engine reads its shape. Any plan that assumes a clean headless core has to deal with that first — and with utils, which has the same problem. Note the type-only guarantee is scoped to src/** by an ESLint rule; 18 test files under packages/element/tests/ value-import from the editor package, many pulling in the Excalidraw component itself.

The three runtime cycles are load-bearing, not accidents. math/src/range.ts:1 needs toBrandedType from common, while common/src/utils.ts:1 needs average from math. Same story for element/src/bounds.ts:16 pulling getCurvePathOps out of @excalidraw/utils/shape. The third is the surprising one: utils/src/export.ts value-imports six editor modules (/appState, /clipboard, /data/image, /data/json, /data/restore, /scene/export) while the editor imports @excalidraw/utils back in six source files (plus one test) — so utils is not a leaf, it sits between element and the editor and depends on both.

03 · The god component

One class holds the editor together

packages/excalidraw/components/App.tsx is 13,848 lines, essentially all of it one React class starting at :616. It owns the canvas events, the interaction state machine, the clipboard, drag and drop, text editing, embeds, the context menu, and the imperative API.

It is also stitched to the public API: roughly half of ExcalidrawImperativeAPI's members are InstanceType<typeof App>["method"] aliases, the rest declared independently. Renaming a private method can therefore change the published type surface.

Eight of its 60+ instance fields — the ones you meet first

Extracted helpers next to it

App.viewport.ts (817), App.drawshape.ts, App.flowchart.ts, App.cursor.ts, AppStateObserver.ts. The extraction is partial and ongoing — new work should extend these rather than grow the class.

The two heaviest methods

onPointerUpFromPointerDownHandler (~1000 lines) and onPointerMoveFromPointerDownHandler (~890 lines). Together they are 14% of the file.

The pointer-down machine

The method is ~490 lines. What follows is its spine, not a transcription — steps are elided at every stage. Three things are worth committing to memory, because each is easy to get backwards. One: the pan check runs first and swallows more than panning — wheel button, Space held, the hand tool being active, or view mode with a non-capturing tool — all gated on a single active pointer, and the first three also on interaction or navigation being enabled. When it fires, the method returns immediately, no PointerDownState is built, and the ladder is never reached. So the hand tool is handled here, not in the ladder: the ladder's last branch names hand in its negative guard, but in practice nothing with that tool active gets that far. (interaction.enabled.tools only accepts laser and custom, so a non-interactive editor cannot keep hand live either — the guard at the top of the method returns first.) Two: text comes before the arrow/line branch, and the last rung is an else if with a negative guard rather than a bare else, so eraser and image fall through the chain; the eraser starts its trail in a separate if afterwards. Three: the window listeners are conditional, and the condition is not simply "not view mode" — it is !viewModeEnabled || isActiveToolPointerCapturing(), so view mode still gets them for a pointer-capturing tool like the laser.

04 · State

There is no single store. There are four.

This is the single most confusing thing about the codebase, and knowing it saves days. Each mechanism has a distinct job, and putting data in the wrong one produces bugs that do not throw.

1 · this.state — AppState

93 top-level fields (packages/excalidraw/types.ts:315-531): UI chrome, the in-progress interaction, active tool, currentItem* style defaults, viewport, selection, binding preferences, collaborators, editor modes. Projected into UIAppState, StaticCanvasAppState, InteractiveCanvasAppState and ObservedAppState — the last is the only slice the Store diffs for history.

2 · Scene — the elements

Elements never live in React state. packages/element/src/Scene.ts owns the array, the maps, the non-deleted caches, frames, and sceneNonce. replaceAllElements rebuilds the maps and bumps the nonce; the selected-elements cache is not rebuilt there. Instead getSelectedElements compares identity on the way in and clears the cache itself when it no longer matches.

3 · Store — change capture

Every action declares its undo semantics with CaptureUpdateAction: IMMEDIATELY (an undoable step), NEVER (the source's examples are remote updates and scene initialization), EVENTUALLY (fold into the next capture). Pick the wrong one and nothing crashes — undo is just quietly wrong. Note a commit often emits no increment at all, returning early when nothing changed, and can emit several, because it flushes queued micro-actions first. The delta maths lives in packages/element/src/delta.ts (2,071 lines).

4 · History — the stacks

HistoryDelta extends StoreDelta, and its applyTo passes excludedProperties: new Set(["version", "versionNonce"]) so an undo looks like a fresh user edit to collaborators rather than a version rollback. That detail exists purely because collab reconciliation compares those two fields.

Mutation: the intent and the reality mutateElement is more conditional than it looks, and every condition matters for collab. If no field actually changed it returns early and bumps nothing. The shape cache is evicted only when width, height, fileId or points appear in the update. And version/ versionNonce are bumped only when the caller did not supply them — just updated moves on every real change. Application code also never calls it directly: it goes App.mutateElement → Scene.mutateElement → mutateElement. Thirteen files import from the leaf by relative path — only six of them want the mutateElement function itself. Others reach it through the package barrel (element/src/index.ts:82), including App.tsx, which calls the raw function at four sites around :12352-12390, each with the comment // NOTE: We use the raw mutateElement() because we don't want history. ConvertElementTypePopup.tsx does the same in three places while also using app.scene.mutateElement elsewhere in the same file. So the chain is the default, not a guarantee: if an edit is missing from undo, check whether the code path bypassed Scene deliberately. Nothing in excalidraw-app/ touches it at all. Mutation happens outside that path too — data/restore.ts:728,793,796,813 assign fields directly and element/src/transform.ts:532,768 use Object.assign. So "all mutation goes through one function" is the design intent, not an invariant.

Jotai is the fifth thing that looks like state but is not. editor-jotai.ts uses createIsolation() from jotai-scope so the editor's atoms never collide with a host app's, and atoms hold UI-local state: dialogs, colour picker, sidebar, library, search, eyedropper. No atom holds the canvas elements — though libraryItemsAtom does hold library items, each carrying its own element array, so "no elements in atoms" would be too strong. ESLint blocks importing bare jotai.

05 · Rendering

Three canvases and two caches

The layers exist so that an expensive repaint is avoided while you are dragging. The static and interactive layers are each wrapped in React.memo with a hand-written comparison. The new-element layer is not wrapped — that missing wrapper, not anything about its effects, is what lets it repaint freely. It is also mounted conditionally, with a sharp edge: Renderer.ts:99 computes the layer's element as newElement?.frameId ? null : newElement, so drawing inside a frame unmounts it and pushes the in-progress shape back onto the static canvas.

Layer Renderer LOC Why it is separate
Static renderer/staticScene.ts 508 The finished drawing. Throttled only when the host sets window.EXCALIDRAW_THROTTLE_RENDER; exports and tests run it unthrottled.
Interactive renderer/interactiveScene.ts 2,102 Selection, handles, binding highlights, remote cursors.
New element renderer/renderNewElementScene.ts 105 The shape being drawn right now, so the static layer is untouched. Not memoized, and not mounted when the new element belongs to a frame.
SVG export renderer/staticSvgScene.ts 801 Hand-kept twin of the static renderer. Drift is caught by tests/scene/export.test.ts, mostly by explicit DOM assertions rather than snapshots.

Cache 1 · the render memo

scene/Renderer.ts memoizes visible-element computation on a canvasNonce, built from scene.getSceneNonce() plus — when the new element sits inside a frame — its versionNonce. If a repaint is not happening, this nonce is the first place to look.

Cache 2 · ShapeCache

A WeakMap of element → generated RoughJS shape (packages/element/src/shape.ts:82-165), evicted conditionally by mutateElement.ts:136, which also clears a second cache, elementWithCanvasCache.

On throttling: renderStaticScene only reaches the throttleRAF wrapper when its throttle flag is true, and StaticCanvas supplies that flag as isRenderThrottlingEnabled() — which reads window.EXCALIDRAW_THROTTLE_RENDER, off unless a host opts in. So tests repaint synchronously because the flag is off and the throttled path is skipped, not because of the throttleRAF mock in setupTests.ts. A few tests set the global to true and do throttle. The catch: it is also read on the geometry path: bounds.ts:968 reads it, and linearElementEditor.ts:2008 calls generateElementShape, which populates it. A cache bug shows up as wrong hit-testing, not just wrong pixels.

06 · Actions

Gating is not one mechanism

Nearly every user command is an Action, and the ActionName union is closed at 98 members. Hiding a command is harder than it looks: there are five checks, each guards a different door, and none of them guards all the doors.

Check Where it is evaluated What it does not cover
UIOptions.canvasActions[name] handleKeyDown, renderAction executeAction — so context menu, command palette and API dispatch walk past it. It is also a closed 7-key set, so most of the 98 actions have no key to set.
action.viewMode handleKeyDown only executeAction and renderAction. The command palette re-implements the check itself.
action.navigation handleKeyDown and executeAction executeAction exempts source === "api".
isActionBlockedByViewportTransition (manager.tsx:89) all three paths Nothing. The only check applied everywhere, and API calls are not exempt.
action.predicate no dispatch path — only inside isActionEnabled, which nothing in the manager calls before running an action Everything, by default. isActionEnabled is a manager method, but it is a query call sites opt into; palette and context menu re-implement it.
Four more things stop an action working, none of them a gate Shortcut collision — handleKeyDown sorts by keyPriority, filters, then bails if more than one still matches, logging "Canceling as multiple actions match this shortcut". A colliding shortcut disables both commands rather than picking one.
No keyTest — unreachable by keyboard.
No PanelComponent — renderAction has nothing to render.
Never registered — register() is a module side effect, so an action in a file nothing imports does not exist at runtime.

41 action* files — 36 action modules plus 5 test files. The one to know is actions/actionProperties.tsx: 2,165 lines containing the entire style panel, and the file every new element property lands in.

08 · Risk map

What will bite, and why

Risk here means one thing: how likely is it that editing this file goes wrong, or that you fail to notice it went wrong. Tier names are written out on every card, so the colour is never the only signal.

Two things the tiers do not capture

packages/excalidraw/subset/woff2/woff2-bindings.ts (4,051 lines) is generated Emscripten output. Treat it as a binary artefact: never hand-edit, exclude it from review.

Six files in element/src have no test file of their own: store.ts, Scene.ts, mutateElement.ts, shape.ts, renderElement.ts, heading.ts. How well each is covered anyway varies: store.ts is exercised hard by tests/history.test.tsx, which asserts on store internals directly; renderElement.ts and heading.ts are referenced by no test at all. The reverse case is common too — groups.ts is tested by tests/zindex.test.tsx, resizeElements.ts by tests/resize.test.tsx, convertToShape.ts by tests/recognizeShape.test.ts, and several more. A filename grep misleads in both directions; grep for the module's exported names instead. The two vendored packages have zero tests.

10 · App shell

The app, and everything it phones home to

excalidraw-app/ is 6,851 lines. There is no router. The app makes two pathname decisions — App.tsx:1266 checks for /excalidraw-plus-export, and an inline script in index.html:110 checks for / before the Plus redirect. Everything else runs off hash and query state (#room=, #json=, #url=) resolved during initializeScene, which then rewrites the URL to the bare origin — except when there is a room link. #room= is deliberately preserved, because the room's encryption key lives in that fragment; room links also skip the overwrite prompt, so no path here erases them. The PWA share target is a different mechanism again: /web-share-target is declared in the vite.config.mts manifest, and the branch that handles it is a query-parameter check inside the editor package.

Collaboration: socket.io for transport, Firebase for persistence 

sequenceDiagram
  participant C as Client (Collab + Portal)
  participant WS as Socket server
  participant FB as Firebase
  C->>WS: join-room (roomId)
  C->>WS: AES-GCM payload, encrypted with roomKey
  WS-->>C: SCENE_INIT / MOUSE_LOCATION / IDLE_STATUS
  C->>C: decryptPayload, then reconcileElements
  C->>FB: saveCollabRoomToFirebase (encrypted scene)
  FB-->>C: fetchImageFilesFromFirebase

Portal and Collab are both client-side classes; only the socket server and Firebase are remote. The room key never reaches the server: the scene is encrypted client-side and the key lives in the URL fragment. reconcileElements does not go straight to versions — shouldDiscardRemoteElement first checks whether that element is the one you are editing text in, resizing, or creating, and only then compares version, with the lower versionNonce as a tiebreak. That version comparison is why HistoryDelta excludes the two fields on undo.

External services in this build

Most endpoints come from .env.production. Several do not: the Sentry DSN is hardcoded in excalidraw-app/sentry.ts, SimpleAnalytics and Google Fonts are in excalidraw-app/index.html, and some URLs are hardcoded rather than read from env (app.excalidraw.com in index.html, the Storage host in data/firebase.ts, blog links in components/EncryptedIcon.tsx and packages/excalidraw/components/HelpDialog.tsx). Three things that are on by default, with no app-level switch 1 — excalidraw-app/sentry.ts maps hostnames to environments and the map includes "vercel.app", so any preview deployment reports errors unless VITE_APP_DISABLE_SENTRY=true.
2 — SimpleAnalytics is a script tag in excalidraw-app/index.html, independent of app code.
3 — the same file redirects / to app.excalidraw.com, but only for visitors carrying an opt-in cookie excplus-autoredirect=true — a different cookie from the Plus auth cookie excplus-auth, so being signed in is not enough. Both this and the analytics tag sit inside a production-build condition, so you never see either locally.

Persistence is per-origin and carries no identity. The full STORAGE_KEYS set is excalidraw (elements), excalidraw-state, excalidraw-collab (just the local username), excalidraw-theme, excalidraw-debug, two cross-tab version stamps, and two IndexedDB keys — plus the files-db store for binary files and one legacy migration-only library key. Not one of them is keyed by a user or document — the only user data in there is the collaboration display name — so anything multi-tenant is new work rather than a change here.

12 · Onboarding

Getting productive

Commands

yarn start dev server
yarn test:typecheck tsc, no emit
yarn test:app vitest, watch mode
yarn test:update single run, update snapshots
yarn test:all typecheck + eslint + prettier + tests
yarn fix prettier then eslint --fix
yarn build:packages ordered esm builds

Run yarn test:update before committing anything that touches rendering or state — 24 snapshot files will move.

Lint rules that will bite

  • consistent-type-imports is an error — type imports must be separate
  • import/order — @excalidraw/** is a pathGroups entry positioned after external, not its own group; type imports are their own group, last; newlines-between is always-and-inside-groups, so blank lines inside a group are allowed. It is a warning, but eslint --max-warnings=0 still fails CI
  • importing bare jotai is banned — use editor-jotai or app-jotai
  • prettier covers md, json, yml, css and html, so docs are lint-gated too

Tests

Vitest + jsdom, with @excalidraw/* aliased to source, so no build step. The readable part is the interaction DSL: tests/helpers/ui.ts (UI, Pointer, Keyboard) and tests/helpers/api.ts (API.createElement, API.setElements). Note render is a re-export of renderApp, so grepping for export const render finds nothing.

CI

Eleven workflows. On pull requests: lint, coverage comment, bundle size, conventional PR title, and run cancellation (which also fires on pushes to release). On push to master: the test suite. On push to release: autorelease, Docker build and publish, Sentry release. The eleventh, locales-coverage.yml, fires only on the Crowdin branch l10n_master.

Deploy

Vercel builds to excalidraw-app/build, with headers including Access-Control-Allow-Origin: https://excalidraw.com. Docker is multi-stage onto a digest-pinned nginx:stable-alpine-slim. Vite inlines env at build time, so the image is not configurable at run time.

  1. packages/excalidraw/index.tsx — the public shape of the thing
